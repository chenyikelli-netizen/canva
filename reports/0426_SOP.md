## Standard Operating Procedure v5.0

> **版本**：v5.0（最終完整版）
> **最後更新**：2026-04-26
> **Reference Repository**：`https://github.com/chenyikelli-netizen/canva`
> **定位**：完全自包含。任何未有前置脈絡的工程師或 AI 模型，可依此文件獨立部署任意追蹤品牌，並產出日報、週報、月報。

---

## 一、系統是什麼

Brand Sentinel 是一套**全自動品牌輿情監控框架**，每天早上 10:00（台北時間）自動完成：

```
蒐集 → 分析 → 報告 → 備份 → 通知
```

你只需要定義「追蹤哪個品牌、競品是誰」，系統每天自動：
1. 從 Dcard、Threads、搜尋引擎等平台蒐集公開討論
2. 用 LLM 標記情緒、主題、品牌歸屬
3. 生成三層報告（日報 / 週報 / 月報）
4. 備份至 GitHub
5. 推送通知至 LINE 和 Telegram

## 二、三層報告架構（目前版本完整內容）

### 日報（每天）

| 區塊 | 說明 |
|------|------|
| KPI | 採樣筆數、品牌防線等級（🟢/🟡/🔴）、資料來源 |
| 情緒雷達 | 正向/中立/負向百分比 |
| 品牌聲量市佔 | 主品牌 + 各競品的筆數與正向感情佔比 |
| 熱議主題 Top3 | 主題名稱 + 事件摘要 + 代表原音 |
| 商業與產品洞察 | 2–3 條 LLM 生成，與投資效益相關 |
| 競品戰略分析 | 1–2 條競品差異解讀及其投資意義 |
| 發展風險預警 | 有則列出 |
| **📌 持倉訊號** | 🟢/🟡/🔴 等級 + **必引今日具體數字的一句話原因** |
| **💡 今日應更新的認知** | 舊認知 → 今日影響（支持/挑戰/未改變）→ 原因 |

**閱讀順序**：先看📌信號 → 若黃/紅則往上讀觸發源頭 → 最後讀💡認知更新

### 週報（每7天，合併在當日 Pro Max HTML 底部）

| 區塊 | 說明 |
|------|------|
| 本週 vs 上週聲量變化 | 筆數增減與百分比 |
| 情緒趨勢對比 | 正向/中立/負向的週 vs 週% |
| 本週主題排行 Top5 | 各主題筆數 |
| **📌 本週持倉信號回顧** | 本週幾天綠/黃/紅 |
| **值得注意的日次信號** | 本週黃/紅的具體日期、原因、認知更新 |

**閱讀順序**：先看信號分布 → 聲量趨勢 → 主題持續性 → 具體日次信號

### 月報（每月最後一次週期，合併在當日 Pro Max HTML 底部）

| 區塊 | 說明 |
|------|------|
| 月度 KPI 四格 | 月度總聲量、月均正向%、負向%、中性% |
| 品牌聲量橫條圖 | 各品牌月度佔比 |
| 各週分段摘要 | 每週起止日、筆數、正向%、負向% |
| **📌 月度持倉信號分布** | 整月幾天綠/黃/紅 |
| **各週代表性認知更新** | 每週取最顯著一筆（紅優先，其次黃）|

**閱讀順序**：月度信號分布 → 各週認知更新（並排看，找是否同一問題重複）→ KPI 跨月比較

### 觸發邏輯（方案 B）

```
距上次週/月報 < 7 天  →  僅日報
距上次 ≥ 7 天 AND 今日+7天 ≤ 本月最後一天  →  日報 + 週報
距上次 ≥ 7 天 AND 今日+7天 > 本月最後一天  →  日報 + 月報
```

若觸發日電腦未開機 → 下次開機第一天自動補發，補發時重新判斷類型

### 認知記錄機制（Memory）

- 每日日報執行後，`investor_signal` + `cognitive_update` 自動寫入 `data/cognitive_log.json`
- 保留最近 90 天
- 週報從 log 讀取本週 7 天資料 → 計算信號分布
- 月報從 log 讀取當月所有資料 → 各週取最顯著信號

## 三、首次部署

### 環境需求

- Node.js v20+
- Git（已設定 `user.name` 和 `user.email`）
- Windows（排程腳本為 `.bat` 格式）

### 步驟 1 — 取得程式碼

```bash
git clone https://github.com/chenyikelli-netizen/canva.git my-brand-sentinel
cd my-brand-sentinel
npm install
```

### 步驟 2 — 設定環境變數

```bash
copy .env.example .env
# 填入所有金鑰（見下表）
```

| 變數 | 用途 | 取得方式 |
|------|------|----------|
| `GEMINI_API_KEY` | LLM 分析 | [aistudio.google.com](https://aistudio.google.com) |
| `TAVILY_API_KEY` | 網路蒐集 | [tavily.com](https://tavily.com)（免費方案） |
| `LINE_CHANNEL_ACCESS_TOKEN` | LINE 推送 | LINE Developers → Messaging API |
| `LINE_CHANNEL_SECRET` | LINE 驗證 | 同上 |
| `LINE_USER_ID` | 推送對象 | Webhook event 的 `source.userId` |
| `TELEGRAM_BOT_TOKEN` | Telegram 推送 | @BotFather |
| `TELEGRAM_CHAT_ID` | 推送對象 | `node get_telegram_id.js` |

### 步驟 3 — 逐項驗證

```bash
npm run test:collect    # 蒐集（會呼叫 API）
npm run test:analyze    # 分析（需 DB 中已有資料）
npm run test:report     # 報告生成
npm run test:line       # LINE 推送測試
npm run test:telegram   # Telegram 推送測試
```

### 步驟 4 — 首次推送 GitHub（只做一次）

```bash
push_git.bat
```

> ⚠️ 此腳本包含 `git init`，**只執行一次**，重複執行會衝突

### 步驟 5 — 建立自動排程

```bash
node install_task.js           # 每日 10:00（主流程）
node install_backup_task.js    # 每日 02:00（資料備份）
```

## 五、每日執行時間表

```
10:00 台北時間 — 主流程（via Windows 工作排程器）
  │
  ├─ 防重複鎖定（.pipeline.lock）
  │     今日已執行 → 跳過（加 --force 可強制執行）
  │
  ├─ Phase 1：蒐集（5–10 分鐘）
  │     TavilyCollector：A本土 / A2評論 / B競品 / C國際商務
  │     DcardCollector
  │     ThreadsCollector
  │
  ├─ Phase 2：分析（3–8 分鐘）
  │     每批 10 筆送 Gemini → 情緒 + 主題 + 品牌 + 摘要
  │     失敗批次排入重試佇列（最多 3 次）
  │
  ├─ Phase 3：報告生成
  │     Markdown 日報
  │     判斷週期性報告（方案 B）
  │     HTML Pro Max 面板（日報 + 週/月報擇一）
  │
  ├─ Phase 4：備份
  │     寫入 Obsidian 本地
  │     寫入 reports/ 目錄
  │     backup_to_github.bat
  │
  └─ Phase 5：通知
        LINE（主）
        Telegram（備援）
        訊息依日報/週報/月報差異化標頭

02:00 台北時間 — 深夜資料備份
  └─ backup_to_github.bat（DB + reports/）
```

## 七、報告閱讀導覽

### 日報（每天 3 分鐘）

```
❶ 先看最底部 → 📌 持倉訊號
   🟢 → 整份快速掃，30 秒
   🟡 → 往上看「熱議主題」+ 「競品分析」
   🔴 → 往上看「情緒雷達」確認比例 → 「風險預警」→ 「熱議主題」找根源

❷ 再看最底部 → 💡 今日應更新的認知
   問自己：「我同意這個認知更新嗎？」
```

### 週報（每7天）

```
❶ 本週信號分布 → 設定本週整體溫度
   全綠 → 平靜週
   含黃 → 看具體日次信號
   含紅 → 仔細讀那天的原因

❷ 聲量變化 → 判斷品牌熱度方向
   聲量↑ + 情緒正向 → 健康增長
   聲量↑ + 負向同升 → 有爭議事件帶動
   聲量↓ → 均值回歸（除非連續兩週）

❸ 主題排行 → 看上週話題還在嗎
   話題持續比話題出現更值得在意
```

### 月報（每月一次）

```
❶ 月度信號分布 → 月度品牌健康度
   0–2 天紅 → 正常
   3–5 天紅 → 月內有結構性事件
   6+ 天紅  → 系統性問題

❷ 各週認知更新並排看
   同一問題重複出現 → 結構性風險
   每週不同事件 → 正常波動

❸ KPI 四格 → 跨月比較
   月均正向率和上個月比
```

### 三層連接邏輯

```
日報：「今天這個信號是真的嗎？」→ 答案在週報裡
週報：「這週是新趨勢還是偏離？」→ 答案在月報裡
月報：「我的投資論點還成立嗎？」→ 答案在你這裡
```

## 九、三大保護機制

### 1. 防重複執行鎖定

```
執行時建立 .pipeline.lock（內容 = 今日日期）
同日再次執行 → 偵測到鎖定 → 立即跳過
跨日執行 → 日期不同 → 正常執行
加上 --force → 無視鎖定強制執行
```

### 2. 週期報告補償機制

```
每次主流程執行時：
  └─ 查詢 DB 中最近一次週/月報發送日
  └─ 若距今 ≥ 7 天 → 方案 B 判斷類型 → 觸發對應報告
  └─ 儲存至 DB，防止重複補發
```

### 3. LLM 失敗回收機制

```
分析批次失敗 → 標記 failed
下次執行 → get_unanalyzed_data() 包含 failed 資料
重新送入 → 成功後 clear_analysis_failure()
連續失敗 3 次 → 永久標記，不再重試
```

## 十、故障排除速查

| 症狀 | 最可能原因 | 處理方式 |
|------|------------|----------|
| 蒐集 0 筆資料 | Tavily API 額度耗盡或金鑰失效 | 確認 `.env` TAVILY_API_KEY 有效 |
| 分析批次持續失敗 | Gemini 輸出格式異常 | 系統自動重試，無需手動處理 |
| LINE 未收到訊息 | Token 或 User ID 錯誤 | `npm run test:line` 確認設定 |
| Telegram 未收到 | Chat ID 錯誤 | `node get_telegram_id.js` 重取 |
| GitHub push 失敗 (404) | PAT Token 過期 | 更新 GitHub Personal Access Token |
| HTML 報告空白 | htmlpreview 快取延遲 | 等 1–2 分鐘後重新整理 |
| 今日流程被跳過 | `.pipeline.lock` 鎖定 | 加 `--force` 或刪除 `.pipeline.lock` |
| 週/月報未觸發 | 距上次未滿 7 天 | 手動執行 `send_weekly_now.js` |
| 持倉訊號/認知更新空白 | LLM 未回傳新欄位 | prompt 已設定不得省略，重新跑一次 |
| cognitive_log.json 不存在 | 尚未執行任何日報 | 執行一次完整流程即自動建立 |
